# BTC/JPY デイトレ戦略 検証ツール（バックテスト専用）

bitbank の BTC/JPY 15分足で、テクニカルなデイトレ戦略を**過去データで検証するだけ**のツールです。

- **注文・売買のコードは一切ありません。** APIキーも使いません（読み込む処理もありません）。
- ccxt は認証不要の公開API（`fetch_ohlcv` でローソク足を取得）にだけ使います。

> ⚠️ **過去の成績は将来の成績を保証しません。**
> バックテストの結果が良くても、実際の売買で同じ結果になるとは限りません。
> このツールの出力は投資判断の根拠ではなく、戦略の「仮説検証」のための参考情報です。

## 構成

```
btc_backtest/
├── backtest.py          # データ取得 / バックテストエンジン / 検証 / 出力
├── config.yaml          # すべての設定（コスト・リスク上限・戦略パラメータ・探索範囲）
├── strategies/
│   ├── base.py          # Signals 型とインジケータ（RSI, SMA, ATR）
│   ├── rsi_reversal.py        # A: RSI 逆張り
│   ├── bollinger_reversal.py  # B: ボリンジャーバンド逆張り
│   ├── ma_cross_atr.py        # C: 移動平均クロス + ATR 損切り・利確
│   └── fixed_time.py          # 比較用: 毎日同じ時刻に買って決済
├── data/                # btc_jpy_15m.csv が保存される
└── results/             # 実行結果（自動作成）
```

## 実行方法

Python 3.10 以上。

```bash
cd btc_backtest
pip install -r requirements.txt

# 1) 過去データ取得（初回は 2017年〜 を1日ずつ取得するので時間がかかります）
python backtest.py fetch
#    再実行すると、CSV の最終日以降だけを追加取得します。
#    途中で止めても、30日ごとに保存しているので再実行で続きから再開します。

# 2) バックテスト（学習期間でパラメータを決定 → 検証期間で評価）
python backtest.py run

# 特定の戦略だけ
python backtest.py run --strategy rsi_reversal
# 別の設定ファイル
python backtest.py run --config my_config.yaml
```

### 出力（`results/`）

| ファイル | 内容 |
|---|---|
| `summary.csv` | 戦略ごとの学習期間・検証期間の成績 |
| `equity.png` | 資産推移グラフ（上: 学習期間、下: 検証期間） |
| `grid_<戦略>.csv` | 学習期間で試した全パラメータの成績（感度の確認用） |
| `trades_<戦略>_test.csv` | 検証期間の全取引（決済理由つき） |
| `chosen_params.yaml` | 学習期間で採用したパラメータ |

成績の指標:
- 総損益（円・%）、最大ドローダウン（足ごとの含み損益込み資産で計算）
- 勝率、取引回数、1取引あたり平均損益（円・%、手数料・スリッページ込み）
- シャープレシオ（日次リターンから計算、年率換算 √365、無リスク金利0）
- プロフィットファクター（参考）

## バックテストのルール

| 項目 | 内容 |
|---|---|
| 取引 | 現物のみ・レバレッジなし・ポジションは最大1つ（ロングのみ） |
| 約定 | シグナルは足の**終値**で判定し、**次の足の始値**で約定（ルックアヘッド防止） |
| コスト | 手数料 片道0.1%、スリッページ 0.05%（買いは高く、売りは安く約定）を毎回適用 |
| 強制決済 | 毎日 JST 23:45 の足の終値で決済。データ欠損でその足がない日は、その日の最後の足で決済 |
| 新規の締切 | 23:00 より後の足の始値では新規に買わない（`last_entry_time`） |
| 日またぎ | 前日のシグナルは翌日に持ち越さない |
| 日次損失上限 | その日の開始時資産から 2% 減ったら当日は取引停止。含み損も判定に入れる（終値で判定 → 次の足の始値で決済） |
| 損切り・利確 | 価格はエントリー時に決まるので足の途中で判定。同じ足で両方に届いた場合は**損切りを優先**（保守的）。損切り価格より下で窓を空けて始まったら始値で約定 |
| 資金 | 初期100万円、毎回資産の100%（`position_size`）、数量は 0.0001BTC 単位に切り捨て |

## 検証方法（過剰最適化を避けるために）

1. データを時系列で**前半60%（学習）**と**後半40%（検証）**に分割（`split_date` で日付指定も可）。
2. 学習期間だけで、`config.yaml` の `grid` にある少数の候補（1戦略あたり最大16通り、超えるとエラー）を試す。
3. 取引数が `min_trades` 以上の候補の中から、学習期間のシャープレシオが最大のものを1つ選ぶ。
4. **検証期間はその1セットだけで1回評価**する。検証期間の結果を見てパラメータを直すと、検証期間も「学習」に使ったことになるので注意。
5. 「毎日同じ時刻に買って決済」（`fixed_time`、既定は9:00買い→23:45決済）は探索せず、比較用として両方の期間で計算。

インジケータは過去方向の計算（rolling / ewm）だけなので、全期間で一度計算してから期間ごとに売買しても、未来の情報は混ざりません。

`grid_<戦略>.csv` で、採用したパラメータの**隣の値でも成績が大きく崩れないか**を確認してください。1点だけ突出して良い場合は偶然の可能性が高いです。

## 戦略の差し替え・追加

戦略は「DataFrame とパラメータを受け取り、シグナルを返す関数」です。

```python
# strategies/my_strategy.py
from .base import Signals, sma, to_bool

def generate(df, params):
    # df: JST の DatetimeIndex, 列 open/high/low/close/volume
    # 各値は「その足の終値時点」で分かる情報だけで計算すること（shift(-1) などは禁止）
    ma = sma(df["close"], params["period"])
    return Signals(
        entry=to_bool(df["close"] > ma),   # True の次の足の始値で買う
        exit=to_bool(df["close"] < ma),    # True の次の足の始値で売る
        stop_dist=None,                    # 任意: 約定価格からの損切り幅（円, Series）
        take_dist=None,                    # 任意: 約定価格からの利確幅（円, Series）
        max_hold_bars=None,                # 任意: 保有本数の上限
    )
```

`config.yaml` に追加するだけで実行対象になります（キー名 = ファイル名）。

```yaml
strategies:
  my_strategy:
    enabled: true
    params: {period: 50}
    grid: {period: [30, 50]}
```

## 結果が悪かった場合に考えられる原因

1. **コストが利益を上回っている**: 1往復で約0.3%（手数料0.1%×2＋スリッページ0.05%×2）かかります。15分足の値動きの多くはこれより小さいので、取引回数が多い戦略ほど不利です。`avg_return_per_trade_pct` が 0.3% より十分大きいかを確認してください。手数料を0にして再実行すると、「戦略そのものに優位性がない」のか「コストに負けている」のかを切り分けられます（比較用で、実際の条件ではありません）。
2. **相場の性質が戦略と合っていない**: 逆張り（A・B）はレンジ相場向きで、強い下落トレンドでは「落ちるナイフ」を拾い続けます。トレンドフォロー（C）はレンジ相場で騙しが続きます。ロングのみなので、下落期間はどの戦略も不利です。
3. **15分足のテクニカル指標の優位性が小さい（または残っていない）**: よく知られた単純なルールは多くの参加者に使われていて、優位性が薄れていることが多いです。
4. **期間による相場の変化（レジームの違い）**: 学習期間と検証期間でボラティリティや流動性が違うと、学習期間で良かったパラメータが検証期間では合いません。2017〜2018年のバブルと崩壊のような特殊な時期が学習期間の結果を左右している可能性もあります。
5. **過剰最適化**: 学習期間は良く、検証期間で悪化する場合の典型的な原因です。候補をさらに絞る、`min_trades` を上げる、隣のパラメータでも安定しているものを選ぶ、などで対策します。
6. **デイトレの制約**: 23:45の強制決済で、利益が伸びる途中のポジションも切られます。日次損失上限で、反発する前に止まる日もあります。
7. **取引回数が少なく統計的に判断できない**: 取引が数十回だと、勝率やシャープレシオは偶然で大きくぶれます。
8. **データとモデルの限界**: 15分足では足の中の値動きの順番が分からない（損切り優先で保守的に処理しています）。板の厚さ・約定拒否・メンテナンス・欠損データは再現していません。実際のスリッページは急変時にもっと大きくなります。

逆に「結果が良かった」ときも、上の5・7・8に当てはまらないか必ず疑ってください。
